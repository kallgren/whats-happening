Blocked by: —

## Question

What builds the page, and how is it scheduled?

**Note the sequencing.** [07 — Build v0](./07-hub-page-layout.md) shipped a pure-links page that
needs no build at all — just a static file, now live at **https://whats-happening-events.vercel.app**.
This ticket is about adding the *data* pipeline underneath that already-deployed page, so it is only
needed once the first research ticket is ready to replace a link with live data.

Settled going in — do not reopen: **static site, regenerated by a scheduled GitHub Action.**
No server, no database, no auth.

**The host is Vercel, not GitHub Pages** — changed by [07](./07-hub-page-layout.md); see its
answer for why. That leaves one extra question for this ticket, ahead of the list below:

0. **How the Action publishes.** Vercel's **Git integration is not currently connected**, so a
   push to `main` does *not* deploy. Either connect it — then the Action commits the regenerated
   `index.html`, the push deploys, and no credential exists anywhere — or have the Action run
   `vercel deploy --prod` with a `VERCEL_TOKEN` secret. The first fits "build it and never touch
   it again" better; the second avoids committing generated output to git history.

Open for this ticket:

1. **Language and dependencies.** Almost certainly a single script that fetches four sources and
   writes one HTML file. TypeScript/Node, or Python? Prefer whatever has the fewest moving parts
   and the least dependency churn — dependency updates are exactly the maintenance Robert does
   not want. Consider whether a static-site generator earns its keep here at all (it probably
   does not, for one page).
2. **Schedule.** Once daily, or more often? Note that GitHub's `schedule` trigger is unreliable
   under load and can be delayed or dropped; a run that misses is a stale page. Decide whether
   staleness is visible on the page itself (a "last updated" line).
3. **Failure behaviour.** If one source throws, does the whole build fail (loud, but no page at
   all), or does that section render an error and the rest publish (quiet, but useful)? Strong
   prior: **publish what worked, fail the job afterwards** so the email still arrives.
4. **Secrets.** The Ticketmaster key as a GitHub Actions secret. Confirm nothing else needs one
   (a `VERCEL_TOKEN` would, if point 0 goes that way).
5. **Repo layout and privacy.** The repo is public and the deployed URL is public. Confirm Robert
   is comfortable, given the artist list would be visible in page source.
6. **Local development.** Can the build run locally against real sources without the Action, so
   changes are testable? This should be trivially true, but state it.
